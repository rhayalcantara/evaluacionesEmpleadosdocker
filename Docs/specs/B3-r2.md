## Crítica 1 (bloqueante): `normalizarParaEnviar` manda `fechaRegistro: null`
- `nuevo()` (vía `eventoNuevo` de bitacora-utils) deja `fechaRegistro: null`, y `normalizarParaEnviar`
  (aprox. líneas 207-220) hace `{ ...evento }` sin quitarlo. El API tiene `FechaRegistro` como `DateTime`
  no anulable y responde **400** `"$.fechaRegistro: The JSON value could not be converted to System.DateTime"`.
  El mismo cuerpo sin esa clave → 201. Hoy es imposible crear un evento desde el flujo real.
- **Corrección:** construir el objeto a enviar **sin** las claves de solo lectura cuando no tengan valor:
  elimina del cuerpo `fechaRegistro` si es `null`/`undefined`/`''`, y elimina siempre `registradoPorNombre`
  (es de solo lectura). `fechaModificacion` puede ir en `null` (el API la acepta) pero también es válido
  omitirla. Implementa algo como:
  ```ts
  const { fechaRegistro, registradoPorNombre, ...resto } = evento;
  const cuerpo: Partial<IBitacoraEvento> = { ...resto, descripcion, fechaEvento, competencias };
  if (fechaRegistro) { cuerpo.fechaRegistro = fechaRegistro; }
  ```
  y envía `cuerpo` (tipado como `IBitacoraEvento` al llamar a `insertardatos`/`updatedatos` con un cast
  explícito `as IBitacoraEvento`, sin `any`).

## Crítica 2 (misma ronda): normalizar la fecha con `fechaISO`
- Hoy se usa `String(evento.fechaEvento).slice(0, 10)`: si llega un `Date` (datepicker) produce `"Sat Sep 05"`.
- **Corrección:** importa `fechaISO` de `../Helpers/bitacora-utils` y usa `fechaISO(evento.fechaEvento)`
  para el cuerpo (cubre `'YYYY-MM-DD'`, `'YYYY-MM-DDTHH:mm:ss'` y `Date`). Si `fechaISO` devuelve `''`,
  `validarEvento` ya habrá fallado antes, así que no hace falta otra comprobación.
